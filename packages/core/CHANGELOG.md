## 2.5.0

### Minor Changes

- b4f7f5b: Move the proving backend to barretenberg 4.2.0 (stable).

  The previous pin, `@aztec/bb.js@4.0.0-nightly.20260120`, matched the on-chain
  verifiers generated by the same nightly. That nightly no longer exists in any
  package ecosystem, which left the Rust mobile prover unable to ever match the
  deployed verifiers. The whole toolchain (bb CLI for verifier generation,
  bb.js for web proving, barretenberg-rs for native proving) is now anchored at
  the stable 4.2.0 release.

  Proof format changes with this: proofs are 8 field elements shorter. SDKs at
  this version only verify against contracts whose verifiers were regenerated
  with bb 4.2.0 — pair the upgrade with the matching deployment.

### Patch Changes

- 86a398b: Reduce masterKey into the BN254 field inside the key derivations.

  `deriveNullifierKey` / `deriveCreditNullifierKey` / `deriveChangeNullifierKey`
  treated their masterKey argument as a canonical field element, but a masterKey is
  `keccak256(signature)` — a uniform 256-bit value that falls below the modulus only
  ~19% of the time. The other ~81% hit `poseidonHash`'s range check and threw
  `RangeError: input[1] out of BN254 field range`, so privacy receive codes failed
  for most wallets on any client that derives through this SDK.

  Both reference implementations already reduce at this boundary — invisi-nexus
  `pkg/kms.bytesToField` and invisi-sdk-rust `bytes_to_field` — so the derived keys
  now match them bit for bit; new cross-language vectors lock that. The reduction is
  applied only to the masterKey operand: invoiceId, creditId and paymentCommitment
  are field elements by construction and stay under the range check.

  Also exports `bytesToField` for callers that need the same byte-string → field
  conversion elsewhere.

### Minor Changes

- 53ddc9c: feat(core): add domain-separated `deriveCreditNullifierKey` (`D_CREDIT_NKEY`) and `deriveChangeNullifierKey` (`D_CHANGE_NKEY`) key derivations (SPEC-028, SPEC-029).

  feat(ipp): authorize response now delivers `creditNullifierKey` and carries `creditId`; payloads gain a `mode` field and no longer prefill `nonce`/`paymentCommitment`/`treeId`; propose and authorize responses now carry `treeId` (SPEC-028, SPEC-029).

  feat(receiver): `createPaymentRequest` selects the payload `mode` and no longer prefills `nonce`/`paymentCommitment`; `creditNullifierKey` is derived on demand. Consumers that read the prefilled fields must now source them from the propose response or compute them via the selected mode.

  feat(payer): consume the server-delivered credit key with two-step verification; add deterministic `deriveChange` for payBlind and source `treeId` from the propose response (SPEC-028, SPEC-029).

## 2.0.0

### Major Changes

- 1b73ab6: Breaking changes for the SPEC-144 wire format and credit authorize flow.

  - **ipp**: wire keys are now converted to `snake_case` at the codec boundary (SPEC-144). The over-the-wire JSON/msgpack field names changed; payloads produced by older clients are no longer compatible.
  - **core**: removed the deprecated `deriveClaimingKey` alias. Use the current key-derivation API.
  - **payer**: `payOpen` userOp `nonce` is now required (typed-data signing and calldata builder no longer fall back to a random nonce). Callers must supply the nonce explicitly.
  - **payer**: added credit authorize derive/verify helpers and new `AuthorizeRequest` fields; credit nonce is now taken from the authorize response instead of being generated locally.

  All `@invisi-labs/*` packages are version-linked and bump together to `2.0.0`.
